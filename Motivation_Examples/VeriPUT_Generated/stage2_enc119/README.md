## 2. Region certification

The query is `assume(R); assert(tr == pi)` at `query_max_tx = 1` over the box R; a
**refutation is a counterexample inside R that leaves the path**, and the driver
answers it by cutting, splitting, punching a hole, or retreating to a pin. For
enc=119 (`driver.log`, verbatim):

    [certify enc=119] region overlaps an unseparated sibling; certifying anyway, the query is what decides
    [cut enc=119 piece 1] checked-arithmetic refutation(s) at source line(s) [27, 35]: 2 refuting witness(es) read on the violated operation's dependence cone, cuts on the same coordinate intersected
    [cut enc=119 piece 1] state.discountBps$23[msg.sender] -> [1, 250], removing 65285 value(s) -- the fewest of the coordinate(s) this refutation offers
    [split enc=119 piece 1] keeping the discarded side state.discountBps$23[msg.sender] in [251, 65535] as a separate piece
    [punch enc=119 piece 1] NOT punched: the refuting witness is not a known member of any sibling path on this box's coordinates, so it is read as one point of a refuting SET and answered by a cut or a retreat, not by a hole
    [retreat enc=119 piece 1] PINNED amount==1 at its x_pi value and carrying on with the others
    [certify enc=119 piece 1] certified with 1 coordinate(s) PINNED at x_pi (partial generalisation): amount==1

So the certified region of the paper's example is a *partial* generalisation: the two
checked-arithmetic refutations (both subtractions: `rate = feeBps - discountBps[msg.sender]`
at flat.sol:27 and `net = amount - fee` at flat.sol:35) cut
`discountBps` down to `[1, 250]`, and `amount` could not be widened off its witness
value at all, which is why the PUT's box reads `amount == 1`. The final box is the one
printed in the parent README.

The raw ESBMC side of a refutation, `singlepoint_enc115.log` (enc=115, the sibling
path that gets **no** test):

    line  12  --path-cov-certify: CERTIFICATION QUERY for unit 'sol:@C@FeeVault@F@withdraw#193'
              path enc=115 depth=6 over 19 bounded input(s) and 3 entry relation(s)
    line  43  ✗ FAILED: 'withdraw:path:115#nonvacuous ... flat.sol line 22 function withdraw'
    line  53  [Counterexample]        (full trace, 161 states, to line 616)
    line 617  Violated property:
                file flat.sol line 22 function withdraw
                sol:@C@FeeVault@F@withdraw#193:path:115#nonvacuous
                path_tr$4 != 115 || path_cnt$5 != 6
    line 694  Properties: 15 verified ✓ 13 passed, ✗ 2 failed
    line 709  SHRINK SUGGESTION for 'arithmetic overflow on mul' — the witness lies outside the
              path on coordinate 'state.feeReceiver' ... retry with state.feeReceiver in [1, 4294967295]
    line 711  RESULT: UNSAFE — 1 checked arithmetic/division assertion(s) were refuted under the
              certification box, so an input the box admits can panic before a normal unit exit

Two properties fail in that run and they mean opposite things, which the log itself
says at line 12: the `#nonvacuous` failure is **by design** (the witness is refuted on
every run that certifies, so a certified box prints `VERIFICATION FAILED`; the verdict
to read is the `RESULT:` line), while the `arithmetic overflow on mul` failure (the `amount * rate`
at flat.sol:31) is the genuine region refutation. enc=115 was then *not* retried — `generalise-result.json`
records it as `REFERRED TO THE COORDINATE GATE`: the refuting witness and the path's own
counterexample agree on every bounded coordinate and differ only on `extcall.rate`
(250 vs 123) and `state.owner`, quantities no test can set, so no cut could separate
them. `driver.log` closes it as `[witness enc=115] ⛔ REFUTED at the single point: this
path gets NO test`. enc=2 is the other non-certified path, and for a different reason:
it is `EXCLUDED FROM THE SLICE by the pins (msg.value: CE 1 outside [0, 0])`.
